# 店员端与合作社端 · 功能交互规格

> 写法见 [README](README.md) 第 1 节。店员端承担礼品闭环 L2 的「发放」一环和自提订单的「交货」一环；合作社端承担带货闭环 L3 的「接单—发货—售后—对账」。
> 两端都在同一个小程序里（分包 `pkg-staff`、`pkg-merchant`），入口在「我的」页，只有后台绑定过的微信身份能看到。

---

## 0. 身份与进入

### 0.1 绑定

| 身份 | 谁来绑定 | 怎么绑定 | 解绑 |
|---|---|---|---|
| 店员 | 运营人员在 A5-5「店员」新增：姓名、所属柜台、手机号（只用于短信通知） | 后台生成「绑定码」（小程序码，24 小时有效，一人一码）→ 店员用自己的微信扫码 → 页面「确认绑定为 {柜台} 店员」→ 点确认 → 绑定完成 | 后台停用后立即失效；店员下次打开工作台即提示「你的店员身份已停用」 |
| 柜台主管 | 同上，角色选「柜台主管」 | 同上；主管同时有店员端权限和后台「本柜台」权限 | 同上 |
| 合作社账号 | 运营人员在 A6-1「合作社」里添加账号：联系人姓名、手机号 | 同样用绑定码；一个合作社最多 3 个微信账号（负责人、发货员、会计），权限一样 | 同上 |
| 营地自提点 | 后台把营地配置成一个「柜台」，类型「自提点」，只有自提核销权限，没有礼品发放权限 | 同店员 | 同上 |

- 绑定码扫码后，如果该微信号已经是别的柜台的店员：提示「你已是 {原柜台} 的店员，确认改到 {新柜台}？」，确认后原绑定作废。
- 一个微信号可以同时是店员和合作社账号（小村子里常见），「我的」页两个入口都显示。

### 0.2 进入与鉴权

| 情况 | 表现 |
|---|---|
| 「我的」页 | 有身份时，在「常用游客」上方出现一行卡片：「店员工作台 · {柜台名}」/「商家工作台 · {合作社名}」，有待办时右侧红点带数字 |
| 打开任一 `pkg-staff`、`pkg-merchant` 页面 | 每次 `onShow` 调 `GET /staff/me` 或 `GET /merchant/me` 校验；失败显示 README 3.7「没权限」状态，2 秒后回首页 |
| 身份被停用 | 弹窗「你的工作台身份已停用，如有疑问请联系运营」，按钮「知道了」→ 回「我的」 |
| 柜台被停用（如季节性关闭） | 工作台顶部红条「本柜台已暂停，不能发放」，扫码按钮置灰 |

**验收**：后台停用店员后，该店员在 1 分钟内（下一次 `onShow`）无法再核销；直接粘贴路由打开也进不去。

## 一、店员端

### S01 店员工作台（F-S1）

**闭环位置**：L2「发放」的起点。起点是游客走到柜台、店员打开工作台；终点是 S02 发放完成或告诉游客下一步去哪。

**页面元素（从上到下）**

| # | 元素 | 说明 |
|---|---|---|
| 1 | 顶栏 | 「{柜台名}」+ 小字「{所属站点} · 今日 {开放时间}」；右侧当前店员姓名 |
| 2 | 异常条（条件） | 柜台暂停 / 网络断开 / 有库存预警时出现，优先级：暂停 > 断网 > 预警 |
| 3 | 今日概况 | 三格：「今日已发 {n}」「自提已交 {m}」「待撤销审批 {k}」（仅主管看到第三格） |
| 4 | 各档库存 | 按档位分组，每种礼品一行：礼品名、余量、预警线；低于预警线标橙「快没了」，为 0 标灰「已发完」 |
| 5 | 大按钮「扫领礼码」 | 占屏宽 80%，高 72 |
| 6 | 文字按钮「扫不出？输入 6 位数字」 | 打开数字键盘弹层 |
| 7 | 次级按钮 | 「扫自提码」「今日记录」「报补货」 |
| 8 | 底部 | 「店员规范」折叠：核对证件原件、只发本柜台可发档位、误操作 10 分钟内找主管撤销 |

**交互**

| 操作 | 反馈 | 系统 |
|---|---|---|
| 点「扫领礼码」 | 调 `wx.scanCode({onlyFromCamera:true, scanType:['qrCode']})` | — |
| 扫到内容 | 带 token 进 S02 | `ev_staff_scan` |
| 点「输入 6 位数字」 | 弹层，6 格输入框，数字键盘；输满 6 位自动提交 | 进 S02，参数 `code=` |
| 扫到的是自提码 | 自动转 S04 | 根据码前缀区分：领礼令牌 `G`、自提码 `P` |
| 扫到其他码 | Toast「这不是领礼码或自提码」 | — |
| 点「报补货」 | 弹层：选礼品、填数量（默认补到预警线 ×3）、备注 → 提交 | 生成补货申请，进 A5-4 运营待办 |
| 下拉 | 刷新库存与概况 | — |
| 断网 | 异常条「没有网络，不能核销」，扫码按钮置灰 | — |

**验收**：断网时扫码按钮不可点；库存为 0 的礼品显示「已发完」。

### S02 扫码结果与发放（F-S2）

**闭环位置**：L2 的核心一步。起点是扫码（或输入数字），终点是「已发放」或明确告诉游客怎么办。出了异常回到 S01 或回到游客端刷新。

**入口与参数**：`token=`（二维码内容）或 `code=`（6 位数字）。

**系统流程**

1. 店员端调 `POST /staff/redeem/check {token|code, counter_id, request_id}`。
2. 服务端把令牌状态置为 `SCANNED`（游客端看到「店员正在核对」），锁定 60 秒，期间其他店员扫同一码返回「正在被 {柜台} 核对」。
3. 返回下面八种结果之一。

**八种结果**

| 结果码 | 店员看到（结果卡标题 · 颜色） | 卡片内容 | 按钮 | 游客端同步 |
|---|---|---|---|---|
| `OK` | 可以发放 · 绿 | 档位「第{X}档 · {档名}」；领取人「张* · {证件类型} · 后四位 2381」；「今年走过 {n} 站 · {m} 分」；游客意向礼品（如有，标「游客想要」） | 见下面「发放步骤」 | 「店员正在核对」 |
| `REDEEMED` | 这个码已经发过了 · 灰 | 「{时间} 在 {柜台} 由 {店员} 发放 · {礼品}」 | 「下一位」；如果是本人 10 分钟内发的，多一个「申请撤销」 | 不变 |
| `YEAR_USED` | 这个证件今年已领过 · 灰 | 「{日期} 在 {柜台} 领了第{X}档」 | 「下一位」；小字「每个证件每年领一次」 | 不变（游客端本来就显示已领） |
| `EXPIRED` | 码已过期 · 橙 | 「请游客下拉刷新领礼码后再扫」 | 「重新扫」 | 不变 |
| `TIER_NOT_HERE` | 本柜台不能发这一档 · 橙 | 「第{X}档请到 {可领柜台列表} 领取」；如游客愿意降档：「也可以在本柜台领第{Y}档（降档后今年不能再领）」 | 「重新扫」；「改发第{Y}档」（需要游客当面同意，点后弹二次确认「已向游客说明降档后今年不能再领」） | 降档确认后游客端码上显示「店员建议改领第{Y}档」，游客点「同意」才继续 |
| `OUT_OF_STOCK` | 这一档礼品发完了 · 橙 | 本档礼品逐个列出余量（都为 0）；「{其他柜台} 还有」 | 「重新扫」；「报补货」 | 不变 |
| `NO_ID` | 游客还没登记证件 · 橙 | 「请游客在『我的 → 常用游客』登记证件后，重新出示领礼码」 | 「重新扫」 | 不变（理论上游客端没登记出不了码，这条用于旧版本兼容） |
| `NETWORK` | 需要联网才能发放 · 灰 | 「网络恢复后再扫，不能离线发放」 | 「重试」 | — |

其他错误：`LOCKED_BY_OTHER`（正在被其他柜台核对）显示「这个码正在 {柜台} 核对中」，按钮「重新扫」；`STAFF_DISABLED` 见 0.2。

**发放步骤（结果为 `OK` 时）**

| 步骤 | 界面 | 规则 |
|---|---|---|
| 1 核对证件 | 结果卡下方勾选框「已核对证件原件：姓名第一个字与后四位一致」 | 不勾选，「确认发放」置灰 |
| 2 选礼品 | 本柜台这一档可发的礼品单选列表：图片、名称、余量；有游客意向的默认选中；余量 0 的置灰 | 必选一件 |
| 3 确认发放 | 底部大按钮「确认发放」；点后按钮进入加载态，防重复点击 | `POST /staff/redeem/confirm {token, gift_id, request_id}`，`request_id` 由前端生成 UUID，同一次重试复用，服务端幂等 |
| 4 完成 | 全屏绿色「已发放」+「第{X}档 · {礼品}」，振动一次（`wx.vibrateShort`）；3 秒后自动回 S01，也可点「下一位」 | 服务端事务：令牌 `REDEEMED`、写发放记录、该柜台该礼品库存 −1、证件当年已领标记；库存低于预警线触发提醒 |

**异常回流**

| 情况 | 处理 |
|---|---|
| 点了确认但网络超时 | 按钮保持加载，自动用同一 `request_id` 重试 2 次；仍失败显示「不确定是否发放成功」+「查一下」按钮 → 调 `GET /staff/redeem/{request_id}` 查结果，不让店员重复点确认 |
| 核对中游客离开页面（令牌被新令牌替换） | 确认时返回 `EXPIRED`，提示「游客刷新了码，请重新扫」 |
| 60 秒锁定到期未确认 | 令牌回到可用；游客端「店员正在核对」消失 |
| 证件对不上（游客拿错证件或冒领） | 店员不勾选，点左上角返回；结果卡下方文字按钮「证件对不上」→ 记一条异常（不打断流程），进 B5 异常提醒 |

**验收要点**

1. 不勾「已核对」不能发放。
2. 网络抖动时连点确认，只扣一次库存、只生成一条记录。
3. 同一码两台手机同时扫，第二台显示「正在 {柜台} 核对中」。
4. 发放后游客端 2 秒内变「已领取」。
5. 第四档在森林公园柜台扫出 `TIER_NOT_HERE`，降档需要游客端确认。

### S02-R 撤销发放（F-S3）

**闭环位置**：L2 的纠错回路。起点是店员误操作（选错礼品、发错人），终点是记录作废、库存退回、游客恢复可领。

| 步骤 | 谁 | 界面 | 系统 |
|---|---|---|---|
| 1 | 店员 | S03 记录里本人 10 分钟内的记录右侧有「申请撤销」；点后选原因（选错礼品 / 游客改主意 / 发错人 / 其他）+ 备注 | `POST /staff/redeem/{id}/revoke-request`；超过 10 分钟按钮消失 |
| 2 | 柜台主管 | 收到订阅消息「{店员} 申请撤销一条发放记录」；S01 第三格数字 +1；点进去看原记录和原因，「同意」「不同意」 | 主管不在：运营在 A5-6 也能审批 |
| 3a | 同意 | 店员端记录变「已撤销」；游客端领取记录卡消失，回到「可领第{X}档」并收到订阅消息「你的领取记录已更正，可重新出示领礼码」 | 记录作废（不删除），库存 +1，证件当年已领标记清除；写操作日志 |
| 3b | 不同意 | 店员端记录标「撤销未通过」+ 主管意见 | — |
| 4 | — | 申请 2 小时内没人处理 | 自动转运营待办 |

**规则**：撤销只能针对「本柜台、本人发出、10 分钟内」的记录；超过 10 分钟的纠错只能由运营在后台处理并写原因。同一店员一天撤销超过 3 次进 B5 异常提醒。

### S03 今日发放记录（F-S4）

**页面元素**：顶部日期切换（只能看最近 7 天；主管能看全柜台，店员只看自己）；汇总条「领礼 {n} · 自提 {m} · 撤销 {k}」；列表每行：时间、类型（领礼 / 自提）、档位或订单号后 4 位、礼品或商品、领取人「张*·2381」、状态（已发放 / 已撤销 / 撤销审批中）。

**交互**：点一行展开详情；本人 10 分钟内的领礼记录有「申请撤销」。不提供导出（导出在后台 A5-6）。

**空状态**：「今天还没有发放记录」。

---

### S04 自提核销（F-S5）

**闭环位置**：带货闭环 L3 中自提订单的终点。起点是游客到柜台出示自提码，终点是订单「已完成」。

**流程**

| 步骤 | 店员看到 | 规则 / 系统 |
|---|---|---|
| 1 扫码或输 6 位数字 | — | `POST /staff/pickup/check {code, counter_id}` |
| 2 结果 | 见下表 | — |
| 3 核对 | 订单商品清单（图、名称、规格、数量）、「收货人 张* · 尾号 {手机后四位}」 | 勾选「已核对商品数量」 |
| 4 确认交货 | 「确认已交货」 | `POST /staff/pickup/confirm {order_id, request_id}`，幂等；订单进「已完成」，游客收到订阅消息「已取货」 |

| 结果 | 显示 |
|---|---|
| 可交货 | 订单详情 + 确认按钮 |
| 不是本自提点 | 「这个订单的自提点是 {自提点}」 |
| 还没备好 | 「合作社还没备好货，预计 {日期}」 |
| 已取过 | 「{时间} 已取货」 |
| 订单已退款 / 已取消 | 「订单已取消，不能交货」 |

**验收**：自提码只能用一次；非本自提点的店员扫不能交货。

## 二、合作社端

> 合作社用户多为村里的合作社负责人、手艺人，手机操作不熟。原则：**一页只做一件事，按钮写动词，字号默认大一号**；不会用手机的合作社由运营在后台 A6-3 代操作，所有代操作留痕并标「运营代操作」。

### H01 商家工作台（订单列表）（F-H1）

**闭环位置**：L3「接单」的起点。起点是收到新订单通知，终点是进入订单详情去处理。

**通知方式**（同时发，避免漏单）

| 事件 | 订阅消息（合作社微信） | 短信（合作社登记手机） | 说明 |
|---|---|---|---|
| 新订单（已付款） | 有 | 有 | 短信：「【红河同路】你有新订单{订单号后4位}，{商品}×{n}，买家在{站名}看完后下单，请在{48}小时内发货。」 |
| 发货快超时（剩 12 小时） | 有 | 有 | — |
| 已超时未发货 | 有 | 有，同时通知运营 | — |
| 游客申请售后 | 有 | 有 | 需 24 小时内回应 |
| 月度对账单出账 | 有 | 有 | 每月 3 日 |

订阅消息每次需要用户授权，合作社容易拒绝或用完次数，所以**短信是主通道**，订阅消息是补充。

**页面元素**

| # | 元素 | 说明 |
|---|---|---|
| 1 | 顶栏 | 合作社名；右侧「对账」「商品」两个文字按钮 |
| 2 | 待办卡 | 三格大数字：「待发货 {n}」「待备货（自提）{m}」「售后待回应 {k}」；有超时的格子变红 |
| 3 | 状态页签 | 待发货 / 待备货 / 已发货 / 已完成 / 售后 / 全部 |
| 4 | 订单卡 | 下单时间、订单号后 6 位、商品缩略图 + 名称 × 数量、配送方式（寄 / 柜台自提 / 营地自提）、「在{站名}看完后下单」、剩余发货时间（「还剩 {h} 小时」，< 12 小时橙，超时红「已超时 {h} 小时」）、主按钮 |

| 订单卡主按钮 | 条件 |
|---|---|
| 去发货 | 寄回家 · 待发货 |
| 已备好 | 自提 · 待备货 |
| 去回应 | 有售后待回应 |
| 看详情 | 其他 |

**交互**：点卡片进 H02；点「去回应」进 H03；下拉刷新；滚动到底加载更多（每页 20）。

**空状态**：待发货为空时「暂时没有要发的货」。

### H02 订单详情与发货（F-H2）

**闭环位置**：L3「发货」一环。起点是订单「待发货 / 待备货」，终点是「已发货」（游客收到通知）或「已备好」（游客收到自提码）。

**页面元素**

| # | 元素 | 说明 |
|---|---|---|
| 1 | 状态条 | 当前状态 + 剩余时间 |
| 2 | 商品清单 | 图、名称、规格、数量、单价；「批次：{来源档案批次}」 |
| 3 | 收货信息 | 寄回家：收货人姓名、手机号、完整地址（发货必须完整，合作社可见；发货完成 30 天后自动脱敏）、「复制地址」按钮。自提：自提点、自提日期 |
| 4 | 下单场景 | 「买家在 {站名} 看完这一站后下单」 |
| 5 | 买家备注 | 有才显示 |
| 6 | 时间线 | 下单 → 付款 → 发货 → 签收 → 完成 / 售后 |
| 7 | 底部按钮 | 见下 |

**寄回家 · 发货**

| 操作 | 反馈 | 系统 |
|---|---|---|
| 点「去发货」 | 半屏表单：快递公司（下拉，常用前置：邮政、顺丰、中通、圆通、韵达、极兔）、快递单号（输入框右侧「扫一扫」读快递面单条码） | — |
| 扫面单 | `wx.scanCode({scanType:['barCode']})` 填入单号 | — |
| 点「确认发货」 | 校验单号格式（6–30 位字母数字）；二次确认「单号 {单号}，确认无误？」 | `POST /merchant/orders/{id}/ship {carrier, tracking_no}`；订单「已发货」，记发货时间（10 天自动确认收货从这里算）；游客收到订阅消息「已发货」 |
| 发完发现单号填错 | 发货后 24 小时内「修改单号」，可改 1 次 | 改后再通知游客一次 |
| 一单多个包裹 | 「再加一个单号」，最多 5 个 | — |

**自提 · 备货**

| 操作 | 反馈 | 系统 |
|---|---|---|
| 点「已备好」 | 二次确认「货已送到 {自提点}？」 | `POST /merchant/orders/{id}/ready`；订单「已备好」，游客端出现自提码，收到订阅消息「可以取货了」 |
| 备货有困难 | 「联系运营」按钮（拨打运营客服电话） | — |

**超时规则**：发货时限默认付款后 48 小时（商品可单独设置，如手作商品 7 天，在商品详情页已写明）。剩 12 小时提醒一次；超时后提醒合作社和运营；超时 72 小时未发货，运营可主动联系游客退款，计入合作社「超时率」。

**验收**：填单号后游客订单详情立即显示快递公司和单号；超时订单在 H01 标红。

### H03 售后处理（F-H3）

**闭环位置**：L3 的异常回路。起点是游客在 P19 提交售后，终点是退款完成 / 补发完成 / 运营驳回，并且订单时间线有完整记录。

**状态机（与游客端 F6-8、后台 A6-4 一致）**

```
游客提交 → 待合作社回应（24h）→ 合作社已回应 → 待运营审核 → 已同意（退款中 / 待补发）→ 已完成
                       ↘ 24h 未回应 → 自动转运营审核
                                              ↘ 运营驳回 → 已关闭（游客可再申请 1 次）
未发货退款：游客提交 → 自动同意 → 原路退款 → 已完成（合作社端只看到订单变「已取消」）
```

**页面元素**：售后类型（退货退款 / 仅退款 / 补发）、原因、游客描述、照片（最多 3 张，点开大图）、申请金额、订单信息、剩余回应时间。

**合作社可做的回应**

| 回应 | 需要填 | 后续 |
|---|---|---|
| 同意退款 | 无 | 运营审核后原路退款；退货退款时游客端显示合作社退货地址，游客填退货单号，合作社收到退货后点「已收到退货」 |
| 同意补发 | 补发快递单号（可稍后填） | 运营审核后订单显示补发单号 |
| 有不同意见 | 说明（≥10 字）+ 可上传照片（如发货前称重照片） | 运营综合判断 |

**规则**

- 合作社不能直接驳回，只能「说明」；最终由运营审核（避免合作社自己决定退不退钱）。
- 生鲜类「不想要了」不支持，游客端已拦截。
- 售后金额从当月对账单中扣减；跨月的在下月扣。

**验收**：合作社 24 小时不回应，售后单自动进入运营待办；退款完成后对账单金额同步扣减。

### H04 对账（F-H4）

**闭环位置**：L3 的终点。起点是每月 3 日系统出上月对账单，终点是合作社确认、运营线下打款并标「已结算」。

**页面元素**：月份切换；汇总卡（订单数、商品金额、退款金额、平台服务费（一期默认 0，按合同配置）、礼品供货金额（如该合作社供应礼品，按核销数 × 单价）、应结金额）；明细列表（按订单：日期、订单号、商品、金额、状态；礼品：日期、礼品、数量、单价）；状态标签。

**对账单状态**

| 状态 | 合作社看到 | 可做的事 |
|---|---|---|
| 待确认 | 「请在 {日期} 前核对」（出账后 7 天） | 「确认无误」「有疑问」 |
| 有疑问 | 「运营正在核对」 | 补充说明 |
| 已确认 | 「等待打款」 | — |
| 已结算 | 「已于 {日期} 打款 {金额}」+ 打款凭证（运营上传） | — |

| 操作 | 系统 |
|---|---|
| 点「确认无误」 | 对账单「已确认」，进运营打款待办（A6-5） |
| 点「有疑问」 | 选具体订单行 + 写说明 → 运营处理后重新出账（版本号 +1），合作社重新确认 |
| 7 天未操作 | 默认确认，提示「已按默认确认」 |

**规则**：一期统一收款、线下打款；二期开通微信支付分账后，这一页改为「分账记录」，结构不变。

### H05 我的商品（F-H5）

**闭环位置**：L3 的供给侧。合作社只能看和申请，改动由运营在 A6-2 审核后生效，确保来源档案和价格经过核实。

**页面元素**：商品列表（图、名称、价格、状态：在售 / 已下架 / 审核中、库存）；每个商品右侧「改库存」「申请下架」「申请上架」。底部「申请新商品」。

| 操作 | 规则 |
|---|---|
| 改库存 | 合作社可直接改，立即生效（这是唯一不需审核的操作）；库存为 0 自动显示「已售完」 |
| 申请下架 | 选原因（暂时缺货 / 换季 / 其他）→ 运营 24 小时内处理 |
| 申请上架 / 新商品 | 填：名称、规格、建议价格、照片（实拍 ≥3 张）、产地村寨、采收或制作时间、批次、配送方式、保质期 → 运营审核来源档案后上架 |
| 新批次 | 「更新批次」：新批次号、采收时间、照片 → 运营审核 |
